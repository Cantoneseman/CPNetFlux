# CPNetFlux AI 协作与项目管理

当前接手入口为 [coordination/START_HERE.md](coordination/START_HERE.md)，其中有六份初始 prompt、环境说明、任务板和角色登记。协作结构为 **总指挥 + 五个专职角色**；原来的五角色章程仍定义专业职责，但不再承担总协调。

总指挥直接与用户沟通，负责澄清目标、优先级、派单、依赖、验收收口和路线纠偏。专职角色通过有版本的任务单执行，并留下各自的文件回执。聊天本身不是唯一事实来源；没有调用或回执证据时，不能声称任务已派发或已完成。

## 五个角色

| 角色 | 主要职责 | 不负责的事情 | 主要产出 |
|---|---|---|---|
| 架构与需求负责人 | 维护问题定义、路线图、架构决策和任务拆分 | 不直接在云端临时改代码 | 决策记录、路线图、任务说明 |
| 实验与证据负责人 | 设计矩阵、固定构建、运行云端实验、分析差距 | 不根据单次结果直接改变协议设计 | 原始结果、环境记录、结论报告 |
| 核心实现负责人 | 在本地分支实现已经批准的方案 | 不自行改变实验口径或路线 | 代码提交、单元测试、变更说明 |
| 测试与质量负责人 | 审查正确性、回归、故障分类、证据完整性 | 不替实现负责人扩大需求 | 测试结果、审查意见、验收结论 |
| 云端运维与发布负责人 | 管理云端构建、磁盘、进程、临时目录和归档 | 不在正式云端源码树直接开发 | 构建清单、运行记录、清理报告 |

## 权威信息顺序

方向与事实分开判断：用户最新明确目标决定方向；当前有效的决策和有版本任务单规定实施范围；代码、实际测试和原始实验记录证明当前事实。若文档与事实冲突，指出差异并修正文档；若实现与用户需求冲突，修改计划和实现，不能以代码现状否定新需求。旧 ROADMAP、聊天和报告只作线索，文档中“已证明”的标签也需要证据。

路线变更必须先写决策记录，再修改实现。旧路线要标记为失效，不能让后续任务继续沿用。

## 本地与云端边界

- 本地 `D:\Project\CPNetFlux` 是唯一的长期开发和审查工作区。即使 Codex UI 显示其他 cwd，所有读取、修改和 git 命令都必须显式针对这个路径。
- 云端 `/root/projects/GridFlux-Beta` 是历史半成品和实验入口，不作为开发分支。
- 云端正式实验只能使用明确记录的提交、归档源码或二进制清单；实验临时目录必须位于 `/tmp` 或明确的实验目录。
- 每个实验开始前检查本地和远端磁盘预算；每个用例结束后删除可再生 payload，只保留日志、摘要、hash 和失败诊断。
- 云端任务结束时报告提交、构建目录、命令、结果目录、磁盘变化、残留进程和清理状态。
- 两端 Windows SSH 别名、最新资源快照、保护目录与操作步骤见 `coordination/ENVIRONMENT.md`。2026-09-17 上海磁盘满，新实验依赖解除此阻塞；不得触碰 `/root/projects/CPSS(DCC)`。
- 总指挥独占维护任务板/角色登记，角色独占自己的回执。共享目录中不并发切 Git 分支或操作 index；实现使用独立 `codex/<task-id>` worktree。

## 任务交接格式

每个 Codex 任务都要写清楚目标和非目标、输入提交、必须阅读的文档、允许修改的目录、验收命令、失败分类、输出文件、提交号和下一任务入口。

任务不能把“性能变快”“实验通过”作为没有数字和证据路径的结论。传输退出状态、独立完整性、wire accounting 和观测证据必须分别报告。

## 当前任务分工

以下是职责，不表示已派发或启动；实际状态以 `coordination/BOARD.md` 的任务单为准。初始化仅阅读、核验、写本角色回执。

- 总指挥：汇总接手回执、处理环境与规格依赖、向用户建议下一步。
- 架构与需求：维护控制连接复用重测后的路线重置，下一阶段聚焦目录数据面阶段耗时。
- 实验与证据：使用固定提交补足代表性小矩阵；暂不把 scheduler 或 hot-path compression 当作性能结论。
- 核心实现：只实现已经写入决策记录的低风险改动；压缩保持显式 opt-in。
- 测试与质量：验证 transfer status 与 evidence status 不混淆，并检查失败是否由资源或环境引起。
- 云端运维与发布：为每次构建生成 commit/二进制 hash，清理临时目录，不触碰 `CPSS(DCC)`。
