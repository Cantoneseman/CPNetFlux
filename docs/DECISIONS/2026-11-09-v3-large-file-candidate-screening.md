## 决定

采用[后续开发计划](../tasks/2026-11-09-v3-large-file-next-plan.md)：
先做一轮有限机制/关键路径预算核对，最多筛选两个新机制，串行执行。

1. 首选TCP大负载帧：源码目前将DATA截断到65532逻辑字节，1MiB chunk有17帧。
   研究减少逐帧I/O/状态/CRC拼接调用，不以增加bufferSize冒充突破帧限制。
   旧64KiB V3热payload诊断已观察到88.514Gbps（稳定性未过门），所以帧数不是根因证明；
   先解释完整文件特有的逐帧成本及预算，否则跳过，不因本路线而自动启动原型。
2. 次选CRC拼接算子：已经缓存幂矩阵，剩余研究是固定长度的等价变换；只有有足够
   关键路径预算才进入，不能因为原语有收益就放宽完整任务>=10%门。
3. 旧population、direct-receive、sender-inline保持关闭；不扩大线程/队列，不改RDMA。
   per-file大页/页布局及系统调优尚无可实施依据，不排为当前实现任务。
4. 两个逐帧机制完成/关闭/跳过后，进入页面管理、搬运路径的独立可行性/候选门，再进入小文件固定开销基线。原计划的小文件研究保留，
   tuned native必须包括已有pending-window auto，不重复包装历史窗口收益。

大帧方案先显式诊断，默认保留旧V3限制。运行时集成前需定稿V3能力协商、
wire/logical上限、控制帧限制、不支持peer拒绝和预算；不得仅修改全局常量。
该门仍开放，不把本路线文件当作具体协议已实现或已定稿。
新模式首轮仅TCP/TLS-off/compression-off；原有默认TLS/RDMA能力不删除。

不采用“继续扩三阶段缓冲/并发”，因为当前没有新的收益证据；不立即并改大帧和CRC，
因为无法分离因果。大帧对比原型>=15%仅用于晋级，完整真实文件仍需五对、
中位吞吐>=10%、CV<=5%及完整性/资源/恢复门；未过门关闭，不无限扩参数。
