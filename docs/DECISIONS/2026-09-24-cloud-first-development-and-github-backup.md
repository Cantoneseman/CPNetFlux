# 云端优先开发与 GitHub 分阶段备份

- 日期：2026-09-24
- 状态：已采纳为项目协作原则；基础设施迁移尚未完成
- 适用：00 总指挥及 01–05 所有长期角色、后续新聊天和续接中的旧聊天
- 范围：CPNetFlux 源码、协作文档、任务管理、构建、测试、结果分析和实验

## 决定

CPNetFlux 采用云端优先的工作方式。迁移验收后，深圳上的独立 CPNetFlux Git 仓库是唯一权威开发工作区。项目相关读写操作，包括代码和项目文档修改、Git 分支/提交、Linux 构建、测试、实验设计与结果整理，都在该仓库或其任务隔离 worktree 中完成。上海只作为跨域传输对端，不建立第二个权威开发副本。Windows 用于登录和管理云端会话、查看结果，以及按任务单紧急回收证据；不作为日常源码或 Git 工作区。

每项可独立审查的操作阶段完成后，必须在对应 `codex/<task-id>` 分支提交明确文件，并推送到身份和权限已核实的 CPNetFlux GitHub remote。对长任务，在阶段边界和高风险操作前先推送可恢复检查点；向用户报告完成前，记录 commit SHA、push 退出状态，并核对远端分支指向相同 SHA。GitHub 是代码、文档、报告、schema、证据索引和小型必要样本的备份，不承载大 payload、全量日志或大型证据包；这些外部证据须保存稳定路径、归属和 SHA-256。

所有提交必须精确列出文件，禁止 `git add .` 混入其他任务内容。不得提交私钥、口令、token、运行时凭据、构建目录或大 payload。推送失败、远端未核实、权限不可用或 SHA 不一致时，明确报告备份未完成，保留当前状态并给出具体阻塞；不得把本地 commit、云端磁盘副本或聊天中的回执说成 GitHub 备份。

## 迁移门禁与当前状态

该原则现在生效，基础设施切换仍未完成。当前 Windows `D:\Project\CPNetFlux` 只是过渡期现有仓库；资料没有证明深圳已存在独立的权威 CPNetFlux clone，也没有证明 GitHub remote 身份、写权限或 push 链路已验收。因此在 `CLOUD-GITHUB-01` 完成前：

1. 新的源码实现、性能实验和会写项目仓库的工作不得继续在 Windows 本地副本展开；先完成云端仓库和安全备份链路的迁移验收。
2. 允许的过渡工作限于迁移所需的只读盘点、逐文件清单/hash 核对、迁移计划，以及用户明确要求的迁移规则文档；这些操作不能冒充已迁移。
3. 迁移任务应只读检查深圳候选 `/root/projects/CPNetFlux` 的存在性、属主、Git 状态、进程占用、挂载点及资源预算；核实 GitHub 仓库身份和凭据管理方式；对本地 tracked、untracked、dirty 内容分类并留可恢复快照；之后在空闲且经批准的独立路径建立新 clone/worktree，逐文件验证迁移范围，完成一次非敏感文档/清单的 commit、push、远端 SHA 回读。任何冲突、未分类文件、活动任务或空间不足都停止迁移，不覆盖现有目录。
4. 现有 `/root/projects/GridFlux-Beta` 是两端 dirty 的历史证据树，禁止作为新仓库、禁止覆盖/清理/就地开发。`/root/projects/CPSS(DCC)` 永远是受保护项目，禁止进入、修改、清理或停止其进程。上海不承担开发仓库职责。
5. 迁移验收后，BOARD 更新任务状态和权威路径；角色聊天必须确认自己的远端会话实际绑定到深圳目标 clone 后才做项目写操作。若某工具只能写本地文件，先停止并报告，不能悄悄回退成本地开发。

## 为什么按阶段备份

“操作完备份一次”在项目执行中按可审查的任务阶段落实：文档或规格交付、代码实现阶段、测试验收阶段、实验计划/结果阶段各自形成明确 commit 和 GitHub push。长构建或实验运行期间不频繁制造无意义提交；在运行前先推送可恢复的任务定义/脚本版本，在结束后推送结果报告与索引，原始大数据按证据流程保存并校验。失败也要留下带清楚状态的记录，不能把失败结果改写为通过。

## 覆盖与不覆盖

本决定覆盖旧角色 prompt、入口说明、历史回执和聊天记忆中“Windows 本地是日常源码/Git/分析工作区、云端只做构建实验”的流程描述；与之冲突时，以本决定、更新后的 `AGENTS.md`/`ENVIRONMENT.md` 和当前任务单为准。它不更改性能目标、实验准入门、云端保护路径、研究结论，也不授权删除数据、停止未知进程、降低认证/TLS 或执行未经任务单列明的外部写操作。
