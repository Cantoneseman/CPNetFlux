## 1. 要保存的想法与边界

用户提出：大文件切成 range，避免单个文件长期占用连接；小文件聚合，摊薄逐文件调度/协议成本。
两者能否统一为可调大小的传输工作单元，并按 workload、资源和运行条件选择高效粒度？
借用 BACS-S 的预算采样思想，先低成本理解负载，再小范围验证候选；借用 BACS-M 的置信度门控记忆思想，
保存“上下文→有效策略及证据”，后续相似任务尽量复用。

本设计采纳该方向，但它是待验证假设，不是现有实现或性能结论。
这里的“微包”指小文件聚合；聚合不等于压缩。首个未来原型应支持 raw 聚合，并以此隔离聚合与压缩的贡献。
目标是降低完整任务完成时间、调度/协议开销和尾部等待，保持校验、资源、恢复与文件交付语义。
不承诺一个通用最优字节数，不承诺首次慢而以后总快，不将此设计解释为当前 40–50/100 Gbps 的解决方案。

本备忘不修改开题正式口径：当前 CPNetFlux 提供压缩决策与文件交付解耦的流式聚合机制，
BACS-S/BACS-M 面向预算约束的压缩选择与策略记忆；当前开题方案的 group/block 粒度仍为配置值。
将“传输粒度”加入可学习动作，是后续扩展假设。需独立验证收益和研究贡献，不能写成 BACS-M 已有能力或天然创新。

## 2. 现有事实与待验证假设

- 已有 range 规划接口见 include/cpnetflux/core/chunk/range_planner.h：
  planAdaptiveRanges / planUnifiedRanges 面向单文件范围；接口本身不证明已有跨文件聚合协议。
- 当前目录扫描先完成元数据清单再进入后续流程。可在同一次扫描顺便累计大小直方图、总字节和文件数，
  但不把“拿到大小分布”当作“已预测最佳传输粒度”，也不为特征再遍历一次目录。
- 既有 tmpfs 实验中，1,000 个 4 KiB 文件扫描中位约 6.79 ms；10,000 个约 75.95 ms；
  S1 cached 下后者约 76.15 ms。8 GiB 单文件 M1 combined 扫描约 0.0369 ms。
  这是历史实验计时，不是本设计新测量，也不能外推到百万文件、冷磁盘或远端共享目录。
  来源：实验目录 2026-11-09-v3-summary-path-22/formal-v2/results.json 和
  2026-11-11-v3-large-file-m1-44/results.json，位于 /home/Su/experiments/CPNetFlux。
- 假设 H1：统一可调工作单元能减少大小文件混合任务的调度开销和长尾。
- 假设 H2：最优区间受文件数/大小分布、端点存储、网络、CPU、并发与内存预算共同影响。
- 假设 H3：预算内的少量代表性验证，加上兼容性和置信度约束的历史记忆，可降低选型总成本。
- H1/H2/H3 均需证据；聚合不能消除目的端每个真实文件的创建、元数据及最终发布开销。

## 3. 统一抽象，不强制所有层使用一个大小

| 层次 | 作用 | 粒度/约束 |
|---|---|---|
| 原始成员文件 | 命名、目录归属、文件完成与发布 | 保持原有用户语义 |
| 决策组 DecisionGroup | 汇总 workload 特征，摊薄一次策略决策 | 可含多个工作单元，成员与布局固定 |
| 调度单元 WorkUnit | 领取、负载均衡、背压与失败重试 | 目标逻辑字节 B，加成员数/等待上限 |
| 编码/恢复块 Block | 独立 raw/压缩、校验及恢复 | 首版可与 WorkUnit 一一对应，协议不永久绑定 |
| DATA 帧/缓冲 | 传输与内存复用 | 遵守协商上限，与 B 独立；一个工作单元可有多帧 |

大文件的一个工作单元通常包含一个文件区间；小文件工作单元通常包含多个完整小文件。
首版优先保持小文件完整入组；容不下的单个较大文件走 range。尾部单元允许不足 B，不能等待填满而死锁。
空文件走有界元数据完成路径；目录及其他特殊文件沿用明确支持范围，不顺带承诺新的文件语义。
是否允许“同一单元混合大文件 range 与小文件成员”留给后续实验；抽象允许，首个原型无需全实现。

推荐 B 为目标大小而非硬等长：受恢复 chunk 对齐、成员数、编码上界、预算与尾部截止共同约束。
不仅限制 bytes，还需 max_members、元数据总字节和最大聚合等待；零字节海量文件仍会耗尽内存。
不将原来的 1 MiB 恢复 chunk、256 KiB DATA 帧或某个 range 值自动指定为新 WorkUnit 大小。
若未来复用现有恢复 chunk，先满足其边界和身份规则；不得让帧随意跨 chunk/file/attempt。

## 4. WorkUnit 草案与数据生命周期

以下是概念字段，尚未确定 wire 格式/API 名称：
- 身份：task_id、unit_id、plan_generation、layout_id；重试另带 lease/attempt。
- 描述：segments[] = (file_id, file_offset, logical_length, unit_offset)；
  logical_bytes、member_count、元数据长度、布局版本/摘要。
- 策略：raw 或 codec/config、独立编码块目录、编码输出上界、解码尺寸上界。
- 资源：预算预留/所有权令牌、当前状态；运行时指针/句柄不直接序列化。
- 校验：块/传输校验与成员恢复进度的明确映射，不能用包 CRC 替代原文件完成语义。

状态建议：planned → admitted → reading → encode_or_raw → ready → sending →
receiving → decode_or_raw → verified/writing → member_completion → published。
这是两端逻辑状态映射，不要求一张全局大锁状态表，也不要求一个单元等全部文件发布才释放全部 buffer。
发送完成 ACK、接收校验完成、落入恢复记录、文件发布成功必须区分，沿用 V3 终态保证。

默认流式构造，不先生成完整 tar/zip 或全任务 staging 文件。
以描述符与有界缓冲连接读取、可选编码和发送；元数据说明每段应回到哪个成员/偏移。
raw 路径只跳过 codec，不跳过边界检查、完整性、恢复和原子发布。
先以“正确且有界”为目标；是否采用 scatter/gather、额外 copy 或新压缩框架留待成本证据选择。

## 5. 并发模型：单元属于任务，不属于线程或连接

读取/构建池 → 可选编码池 → 有界就绪队列 → 空闲传输 lane
接收 lane → 有界接收队列 → 可选解码池 → 文件写入/恢复/发布

- 工作单元属于 task/plan；worker/lane 临时领取。C1 处理 B1、C2 处理 B2，
  B2 先就绪可先由 L1 传输，B1 随后由 L2 传输；接收端按身份/布局还原，不依赖完成顺序。
- 不将“一条线程=永久一个微包=永久一条连接”固定绑定；那会使不同文件/压缩成本产生长尾。
- worker 可本地填充小型构建器以降低共享锁，但受任务统一预算约束，到阈值/截止就提交独立单元。
- 每个编码 worker 持有自己的 codec context。首版使用单线程 codec 加固定外层池，
  避免外层 worker 数乘 codec 内部线程数导致过度并发；raw 不占用编码 CPU 工位。
- 先让一个单元由一条 lane 顺序发完；要跨 lane 并行，应在调度前拆成独立单元。
  不先增加单个编码流的多 lane 重排复杂度。
- 按单元独立编码/解码；避免跨单元隐式字典依赖。若复用只读字典，必须版本固定、显式声明并可恢复。
- 磁盘顺序性与公平性同时考虑：限制单文件在途数量，允许短任务有界优先，记录 starvation/长尾。
  不默认随机抢占所有文件范围就一定更快。

预算使用字节信用和成员数信用，不能只限制队列长度。
发送端需计 raw 在途 + encoded 最坏输出 + codec workspace + metadata + transport 持有；
接收端需计 encoded + decoded + writer/backlog + workspace + metadata。
输入和输出同时存活的峰值必须覆盖；mmap/kernel buffer 等独立账本也需单列，不能隐藏到预算外。
可在 admission 时预留后续最坏转换空间，或使用可证明无环的分级信用；
不得出现所有 worker 拿着输入、一起等待输出内存而死锁。取消、失败和重试需恰好一次归还所有权。
本备忘不增加当前 64 MiB payload 等预算；未来另按原型全持有者核算可行粒度。

## 6. 如何选择粒度：寻找性能平台，而不是神奇常数

局部服务成本可用 t_unit ≈ h + βB + γn 帮助解释：
h 是每单元固定开销，B 为逻辑字节，n 为成员数。
这不是可直接相加预测完整流水线时间的模型；真实任务还受最慢阶段、并发、I/O、排队、尾部与恢复影响。
B 太小会增加调度/协议次数；太大会降低可并行单元数量，增加缓冲占用、重试损失和队尾等待。
网络 BDP 是在途数据参考，不能直接等同最优单元大小。

固定线程/连接/codec 和预算后，从少量合法候选验证。
在完整任务时间差异不超过测量噪声的候选中，优先更小内存、更低尾延迟、更易恢复者，
而非追逐单次最大 Gbps。具体候选值在重启设计时按预算与源数据确定，不在本备忘假定一个最优值。

选择方法：
1. 扫描时顺带累计按文件数和按字节加权的大小分布、分位数/桶、头部大文件占比、
   小文件成员密度、目录数量/深度等有界特征。仅均值不够。
2. 加入端点存储类别、网络模式/能力、连接数、校验/持久化语义、预算、CPU 和实现版本。
   特征缺失保留 unknown；不要用昂贵探测填满所有特征。
3. 基于预算先排除会内存超限、单元不足以覆盖并发、成员过多或恢复不合法的候选。
4. 在代表性层中做有界服务验证；首个文件/目录前缀可能有序偏差，应按大小层和目录来源分层抽样。
   预算耗尽就返回可用固定策略，不无限等待“足够置信”。
5. 只有尚未发出的新决策组可切换策略。可利用本次任务早期真实工作采样，但必须保证已发单元布局不变，
   并将这种在线选择的总时间与冷启动/缓存命中情况分别记录。

预算必须覆盖特征额外成本、查表、探测、低成本确认及误选代价。
以完整任务 T_ready 为主目标，调优开销要计入任务；单独 report 决策时间、有效传输、尾部和恢复成本。
小任务或收益余量不足时直接固定策略；不是每个组都重新花一遍全任务采样预算。

## 7. BACS-M 思路的扩展：存证据，而不是“文件后缀→大小”

| 记录部分 | 建议内容 |
|---|---|
| 上下文键 | count/byte-weighted 分布、总量、目录特征、端点类别、transport、并发、内存、校验/持久化、版本 |
| 策略值 | 候选 B、成员上限、截止/公平规则；codec 作为分离维度或先固定 |
| 质量证据 | 样本量、样本范围、完整任务/阶段成本、方差/置信度、资源与失败记录、时间及实验来源 |
| 有效性 | schema 版本、实现兼容边界、环境漂移、过期/降权策略 |

命中且上下文兼容、置信度足够：采用策略并做预算内低成本确认；
部分相似或证据薄弱：只用来缩小候选；
环境/版本/负载变化或观察显著偏离：降权或失效，在剩余预算内重探，必要时回退固定策略。
缓存本身需有容量上限、原子持久化、损坏回退和并发访问语义；不能无限积累所有原始样本。
策略记忆不保存或复用文件校验完成事实，不替代 manifest，也不能据此跳过源身份检查。

避免首版联合搜索“codec × block × WorkUnit × lanes × pool_size”。
先固定 codec=raw、连接/线程数测试单元粒度；再验证分离的压缩选择；
仅有证据表明耦合收益值得复杂度时，再研究联合策略。较快实现不等于不计决策成本。

## 8. 正确性、恢复及协议边界

- 成员路径规范化和根目录约束；拒绝越界、整数溢出、非法/重叠映射、超成员/元数据/解压上限。
  目录创建、源变化、重复文件标识和重复投递均须定义一致行为。
- 接收前能力协商，明确聚合/布局版本；不支持的 peer 在 payload 前拒绝或选择双方支持的 V3 模式，
  不走 V3 以前的运行时。
- 计划、成员映射和编码块目录持久化或可确定性重建；为 in-flight 单元冻结 plan_generation。
  恢复时不按新缓存策略重新切割已发范围；缺少必要计划时明确拒绝/新建 generation，
  不猜测 offset 或将旧 verified 状态套到新布局。
- 重复/乱序数据按 task/unit/generation/attempt 去重认证；过期 lease 不能提交。
  半包/半块、错误 checksum、截断或解压失败不能将整个单元或成员标记成功。
- 大文件所有区间验证完成后才能发布；一个 bundle 中某成员失败不能误认证其他未完成成员。
  发布/权限等仍按支持的逐文件语义，不能把“一个包到达”宣称目录原子交付。
- 中断、取消、磁盘满、元数据失败、codec 错误均回收 buffer/credit，
  保留可重试范围；支持范围内重试/恢复的成本也纳入评估。

## 9. 未来重启后的顺序与最小证据

以下是候选研究计划，**本轮不得执行**：

| 阶段 | 核心交付 | 验证问题 |
|---|---|---|
| F0 固定 raw 机制 | WorkUnit/布局、大小文件映射、有界队列、成员恢复 | 相对当前 V3，减少了哪些每文件/每范围成本？ |
| F1 固定粒度对照 | 少量合法 B，固定其他条件 | 是否存在稳定平台？是否因 workload 不同迁移？ |
| F2 预算选择 | 扫描顺带特征、分层验证、有界预算与固定回退 | 包括探测成本后是否优于最佳可用固定策略？ |
| F3 策略记忆 | 兼容/置信度/漂移门、持久化 | 重复与相似任务是否更省决策成本？误命中代价多大？ |
| F4 编码协同 | 独立压缩/解压块和池；再评估联合策略 | 聚合、压缩、策略记忆的收益能否分别归因？ |

对照至少区分：现有 range/逐文件 V3；固定 raw 聚合；预算粒度选择无记忆；带记忆；
需要评价压缩时增加固定粒度 raw/codec 对照。使用同提交、相同完整性/持久化和预算。
负载覆盖大文件、小文件、长尾混合；目录数量、相同字节不同文件数及冷/热存储按假设选择。
完整任务有效字节率、files/s、T_ready、决策开销、CPU/GiB、内存峰值、队列尾部及恢复成本同时记录；
压缩时分别报告逻辑字节与实际 wire 字节。不要用压缩后逻辑速率冒充链路速率。

优先证明聚合确实减少当前每文件协议/调度工作；若只在外部包装 tar 后整体传输，不算实现该 V3 设计。
核心正确性覆盖多成员乱序/重复、跨尾块、取消、损坏/截断、预算耗尽/死锁、源变化、
部分成员失败与恢复、策略缓存损坏及版本失效。随后才在合规实机条件下比较性能。

## 10. 重启时必须定稿的少数选择

1. WorkUnit/Block 与现有恢复 chunk 的确切映射和 wire 能力；首版是否一一对应。
2. 首个目标 workload 与文件语义；大小文件混排、公平策略和最大成员数。
3. 在既定预算下的合法 B 候选、池大小和 deadline；单元未完成时的信用释放点。
4. 固定策略基线、探测总预算、兼容/置信度判据及避免误命中的证据。
5. 对开题的正式表述是否扩展，以及与已有聚合/分段/自适应调参工作的区别。
