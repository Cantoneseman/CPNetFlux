## 1. 论文问题与候选故事

### 研究问题

在科学工作流的结果目录交付中，若大文件范围和小文件成员可以进入同一套有界调度工作单元，同时仍按原始文件/范围完成校验、恢复和发布，能否比一个强的分离式调度器缩短端到端“可用”时间？当负载间的有效粒度不同时，在线探测的净收益能否覆盖其自身成本？

### 候选贡献（均待验证）

1. **问题证据：** 识别目录规模、文件粒度和数据量怎样改变端到端完成路径，区分可优化的调度/协议等待与不可避免的读、写、校验、逐文件创建及发布成本。
2. **机制：** 以统一的 WorkUnit 作为调度与负载均衡单位，允许一个大文件 range 或多个完整小文件成员成为一个 WorkUnit；其边界不改变原始成员身份、校验和恢复状态。
3. **策略：** 用目录元数据及有上限的在线探测选择工作单元粒度；只有把探测、决策和可能的试探流量计入完整任务后，仍优于固定/仅元数据策略，才主张“预算感知”。
4. **证据边界：** 在受控合成负载、至少一个真实科学工作流目录以及明确的双端环境中验证。若只在 R770 双机验证，论文只能声称在这些机器、链路、文件系统和配置上成立，不能写成生产 HPC 普遍收益。

这些是论文假设而非已证实的新颖性。完成相关工作核查前，不使用“首次统一”“首个自适应”等优先性表述。策略记忆/BACS-M、压缩/BACS-S、压缩率和历史策略复用不属于首篇主张；主要对照固定为 `raw`，压缩关闭。

## 2. 系统、工作负载与计时合同

### 2.1 系统事实边界

- V3 已有目录清单、受限文件级并发、单文件范围/分块路径、逐文件校验和恢复等能力；这些事实不代表已有跨文件 WorkUnit 聚合。
- 本方案撰写时 checkout 与 GitHub 分支已分叉/进度不同：撰写时 HEAD 为 `cf50d67`，交接时 origin 为 `bceaf3c`。后一提交含压缩功能，尚未确认它对 raw 路径和执行计时的影响。E0 需要基于实际文件审阅差异、验证 raw 明确关闭、记录新 commit 并双端构建/哈希；完成前不启动 E1。
- 统一 WorkUnit、跨成员映射、相应恢复状态与粒度选择器均为待设计/待实现机制。E2–E4 必须等研究原型存在并通过正确性门后再运行，不得把现有 pending window 或按文件队列重新命名成 WorkUnit。
- 当前研究基线是限定环境的 V3 TCP 候选，不等同于 native verbs、磁盘持久化、生产 HPC 或 100Gbps readiness。实验需记录实际 transport；TCP 即使绑定 RDMA 网卡，也只能记为 TCP。
- 在线“预算”定义为探测消耗的墙钟时间及实际读取/发送的探测字节上限。RAM 只作为安全资源观测和实现约束，不作为论文问题的前提。

### 2.2 目标工作流

候选场景是仿真完成后的结果目录交付：计算端产生大结果文件、并行任务日志及目录元数据，分析/归档端收到后需能按原始路径读取。WRF 是候选来源而非已选定或已验证的数据集：官方文档说明 MPI 运行会产生每个处理器的 `rsl.out.*`/`rsl.error.*` 日志，并依设置产生 `wrfout` 及可选 restart 文件（[WRF Running](https://www2.mmm.ucar.edu/wrf/site/documentation/users_guide/running_wrf.html)、[WRF Troubleshooting](https://www2.mmm.ucar.edu/wrf/site/users_guide/troubleshooting.html)）。实验必须先取得一次成功运行的真实目录并测量其组成；若日志数量/字节很少，不得把 WRF 包装成小文件密集负载。

至少保留两种清单：

- **完整交付目录：** 明确列出的工作流输出、必需日志、普通/空目录；用途是评价实际交付。
- **结果文件-only 负对照：** 只含主结果文件。若目录不再受小文件调度影响，应呈现不获益或接近不变，而不是隐藏这一结果。

合成负载用于因果控制，真实目录用于外部有效性。若只有一个真实工作流，论文结论限于该工作流和受测负载范围；要写“科学工作流普遍适用”，至少要增加第二个独立工作流。

### 2.3 主要指标 `T_ready`

主指标是**端到端就绪墙钟时间**：从实验驱动器开始处理一个静止、内容已冻结的源目录（首次目录扫描之前），到接收端所有要求的文件和目录按原始路径存在、内容校验通过、发布状态成功且可供下游读取为止。

计入 `T_ready`：源清单扫描、计划/策略选择、探测、建立连接、传输、重试、接收校验、恢复记录、必需文件创建、最终发布、外部 checksum/tree 验收。只排除一次性软件安装、建集合/端点、数据集生成和单次实验之前的凭据配置；任务提交和运行时凭据失败不能计为快/慢性能样本。

报告但不与 `T_ready` 相加的阶段数据：扫描、计划/探测、连接、有效传输、接收校验、持久化/发布、队列等待、总逻辑字节、重复传输字节。阶段若重叠，以墙钟关键路径为主，不把子阶段时间直接求和。

每次运行结束后独立验证：相对路径集合、文件/目录/空目录数、每个文件 SHA-256、总逻辑字节；源在开始与结束时身份一致。未通过完整性/发布门的运行记为 correctness failure，不能算性能 outlier 后删除。目录不支持的元数据（权限、owner、ACL、xattr、symlink 等）明确排除并固定输入类型，不能隐式宣称保留。

## 3. 公共实验协议

### 3.1 环境和隔离

- 先记录机器、CPU/NUMA、内存压力、文件系统和挂载选项、可用空间、网络路由/接口、内核/驱动、NIC/HCA、实际 transport、绑定地址、TCP/verbs 配置、线程/连接数、程序 commit 与两端二进制 SHA-256。
- 第一阶段固定一个传输模式与连接并发，先用同一 V3 配置诊断；候选比较期间不改路由、网卡系统参数、RX/TX 队列、内核或服务配置。网络/RDMA 计数器保留运行前后差值。
- 若测试 TCP，数据通道显式绑定配置认可的直连地址并标注 TCP；若测试 native RDMA，需确认 RDMA 构建启用、实际选择 `data_transport=rdma` 且两端 QP/摘要证据一致。未满足就不称 verbs。
- 先做短 pilot 并检查磁盘/内存余量。任何输入或目标可能占满用户目录、影响其他任务或需要系统级调优时立即停，先申请容量/时段方案。不得以“内存通常充足”为由不记录峰值和余量。
- 每个运行使用唯一目录和新目标；不清理已有实验现场或不明文件。目标清理由本轮明确创建且清单核对过的路径负责。
- 一次只允许一个写入者/一组实验。R770-2 只按固定提交构建和作为对端，不独立改代码。禁止未提交树、不同 commit 或未验收二进制互传。

### 3.2 运行随机化、重复与统计

- 先做每个条件 1 次 pilot，核对资源、安全和正确性；pilot 不计正式样本。
- 正式因果对照采用按负载分块的配对运行，组内随机化顺序；每个条件至少 7 个有效配对。首轮后若配对差值的 95% bootstrap CI 仍跨越 0 且不能排除 5% 的实用效应，增加到 10 配对；总量上限 15，仍不清楚就报告 inconclusive，不无限追加。
- 每轮使用新的目标；不能在 A/B 中只让一个条件命中缓存。冷/热缓存、tmpfs/磁盘、TCP/verbs 是分层条件，不混在一个均值里。不得未经批准用 `drop_caches`；数据大于可用 cache 或按预先规定的相同读取顺序控制，并记录其含义。
- 主要统计用配对 `T_ready` 比率（candidate/control），报中位数、分布、95% bootstrap CI 和所有样本。报告文件系统、环境和失败样本；不以单次最大 Gbps 作为结论。
- 预先定义有效性门：正确性全通过，源固定、配置固定、运行资源门通过、接口/进程证据完整。认证失败、输入变化、环境污染或计数器门失败时标为无效/中止并解释，不可当作性能结果。
- 最小有意义提升暂定为 `max(5%, 2 × MAD(log(T_candidate / T_control)))`，其中 MAD 在 pilot 配对差值上计算。在 pilot 完成后、打开正式候选结果前冻结该阈值和全部条件；若测量噪声过大，先修实验设计，不事后降低门槛。

### E1：文件数增加时，`T_ready` 的增长来自哪里？

**假设 H1：** 固定总字节和大文件部分，仅增加小文件成员数，会使当前 V3 的完整目录就绪时间明显增长；其中存在可识别且候选 WorkUnit 有机会减少的排队/调度/协议关键路径，而非全部来自必需文件操作。

**阶段 A（pilot）：** 固定总逻辑量 1 GiB：一个 768 MiB 大文件 + 256 MiB 小文件集合。小集合按 1,024 × 256 KiB、4,096 × 64 KiB、16,384 × 16 KiB、65,536 × 4 KiB 四种布局生成；保持文件总字节、目录层级和数据内容规则不变。附加大文件-only 768 MiB/1 GiB 诊断组和完整目录校验。

**阶段 B（正式）：** 仅在 pilot 资源余量充分、计时长度/噪声可接受时，把总逻辑字节统一放大到 8 GiB（6 GiB 大文件 + 2 GiB 小成员），对应 8,192 × 256 KiB、32,768 × 64 KiB、65,536 × 32 KiB、131,072 × 16 KiB。若文件系统/时间不适用，先由研究负责人冻结更小的共同总量，不要擅自缩小其中个别条件。

**测量：** 当前 V3 raw、固定连接/worker/校验/发布语义；每个条件至少 7 配对。记录 `T_ready` 与已有可用阶段计时、CPU/IO、文件系统调用/字节、网卡/HCA 计数。若需要 `strace`/profiler，单独诊断运行并报告观测扰动，不以其作为主性能数据。可做同主机纯文件创建/读写/哈希成本对照，明确它只是 filesystem lower-bound 诊断，不等价于网络协议成本。

**回答：** 文件数是否与端到端变慢相关；差值有多少能由必须的每成员操作解释；关键路径上是否存在候选调度层能影响的部分。E1 不单独证明 WorkUnit 会加速。

**停止门：** 若从 1,024 到 65,536 个成员的 `T_ready` 增量低于预注册实用效应，或增长几乎全是目的端必需创建/校验/发布成本，暂停“文件粒度导致可优化瓶颈”的故事，不进入 WorkUnit 性能主张。

### E2：是否存在一个固定粒度无法兼顾不同负载？

**依赖：** 需有可选择固定 WorkUnit 目标的正确原型；原型和参数必须冻结、可重复，并能恢复原始成员语义。E1 通过后才开始。本实验找性能面，不先声称在线选择。

**负载：** 8 GiB 等总字节的四类合成目录：

| 类别 | 目录构成（示例，实施前由容量门核准） | 目的 |
|---|---|---|
| Large-dominant | 8 × 1 GiB | 范围调度参照 |
| Small-heavy | 65,536 × 128 KiB | 高成员数与可观测 payload |
| Mixed | 4 × 1 GiB + 32,768 × 128 KiB | 同任务大小混合 |
| Long-tail/bimodal | 2 × 2 GiB + 65,536 × 64 KiB | 重尾/双峰与长尾 |

另测真实完整交付目录和结果-only 负对照。所有生成负载的文件字节、布局、生成器版本和完整 manifest 冻结；不使用稀疏文件伪装传输字节。

**粒度：** WorkUnit 目标字节 `B ∈ {256 KiB, 1 MiB, 4 MiB, 16 MiB, 64 MiB}`；完整小文件只能整体纳入，且 `max_members ∈ {16, 128, 1024}`；空尾单元按截止时间/剩余成员提交，不等待填满。对每个候选，报告实际单元大小/成员数分布及总单元数。DATA frame、校验 chunk、恢复身份不随 `B` 暗中变化；若原型无法解耦，明确作为设计限制并先修改研究设计，不得将其混淆为独立 WorkUnit 效应。

**设计：** 15 个候选先做 3 个配对筛选样本/负载；保留各负载前三个候选及一个全局候选，做至少 7 个正式配对。若筛选阶段噪声很大或有候选差距落在噪声内，扩大验证而不是把筛选胜者当结论。

**回答：** 不是各负载最优 `B` 是否不同，而是最优点/近优平台是否不同，以及在未参与调参的负载上，一个训练集选出的固定 `B` 是否产生超过实用门槛的 `T_ready` 损失。逐负载事后最优只作 oracle ceiling，不作可部署基线。

**继续门：** 至少一个 held-out 负载上固定配置相对负载专属配置损失超过实用门槛，且 CI/方差足以辨别；否则不需要增加在线探测，优先固定配置。

### E3：统一调度是否优于最强分离式调度？

**依赖：** E2 原型、相同正确性/资源契约，且可独立配置 WorkUnit 规划。分离式基线必须先调到稳定而非故意做弱。

**比较组：**

- **S0 当前 V3：** 未引入跨文件 WorkUnit 的现有实现，作为工程基线；
- **S1 strong separated：** 大文件 range 与小文件完整成员各自排队/设粒度，但共享同一总 lane/连接、in-flight byte credits、CPU/内存预算和 work-conserving 资源池；分别调优两种粒度，允许短任务借空闲资源；
- **S2 unified：** 同样资源上限下，range 与小文件成员进入统一 WorkUnit 队列/规划器；
- **Ablations：** S2 去掉在线选择（固定 `B`）、去掉跨类 work-conserving 调度、固定 `max_members` 或关闭 probe。每项只回答一个机制，不叠加不必要的参数变化。

所有组固定 transport、数据集、完整性/恢复、缓存策略、CPU/连接并发、总在途字节、目标发布语义。各策略只用训练集调参，held-out 任务用于最终比较。比较 S2 对 S1 是论文机制关键；只赢 S0 不能证明“统一抽象”优于强分离方案。

**回答：** 收益究竟来自小文件合批、WorkUnit 统一负载均衡，还是仅来自资源共享/重调参；它是否降低关键路径空闲/尾部，而非只减少单元计数。记录 per-class 服务时间、lane idle、queue wait、尾部最后 1% 完成时间，作为 `T_ready` 解释指标。

**继续门：** S2 对 S1 的 held-out 中位 `T_ready` 改善达到实用门，配对 CI 支持正收益，且其他负载类无超过 5% 的不可接受回退；否则只报告合批/调度实证，不主张统一 WorkUnit 性能贡献。

### E4：在线探测/预算感知选择有净收益吗？

**依赖：** E2 显示粒度选择有实际代价；E3 的机制能提供安全的固定回退。研究实现不能改变已发 WorkUnit 的布局；未发部分才能应用新策略。每个已探测字节/重试字节和探测耗时都计入 `T_ready`。

**对照：** (a) 训练集上选出的全局固定配置；(b) 只用首遍目录扫描得到的元数据特征选择；(c) metadata + 有上限 payload/time probe 的 selector；(d) 逐测试负载事后最优 oracle，仅作上界。

**预算定义：** 主策略的单次探测上限同时设 payload cap 和墙钟 cap，先触发者停止；候选 cap 在 pilot 后冻结（建议初始评估 `min(1% logical bytes, 2 s)`，并报告 `0/0.25%/1%/4%` 字节 cap 与 `0/0.5/2/5 s` 时间 cap 的敏感性）。如果任务比 cap 更短、探测不能安全进行或资源门将失败，立即回退固定/元数据策略。该数值只是待测设计点，不能在结果出来后挑最好预算而隐去其它点。

**拆分：** 以工作流/负载模板和环境为分组做 leave-one-workload-out（样本足够再做环境留一）；同一生成器/同一运行不能同时用于训练选型及测试评估。报告 selector 的额外字节、探测墙钟、总 `T_ready`、超预算回退率和误选后悔值。

**回答：** 在留出工作负载上，在线 probe 是否比元数据 selector 和全局固定策略多获得净 `T_ready` 收益。Oracle 只显示理论上限，不能用于宣称胜过实际系统。

**删题目条件：** 如果 probe 仅胜过固定值而不胜过 metadata-only，或未覆盖自身成本后没有实用净收益，则论文题目/主张移除“预算感知”，用成本更低的策略。

### E5：性能提升是否以破坏成员恢复/完整性换来？

**依赖：** WorkUnit 正确性测试通过；明确协议状态、lease/attempt、写入、校验、checkpoint 与发布次序。测试不等同于生产 durability certification。

**故障点：** (1) 一个 WorkUnit 部分传输时断客户端/网络；(2) 接收端已写入并验证但恢复事实尚未持久记录；(3) 恢复事实记录后进程退出；(4) 最终成员发布/目录完成事实过程中接收端退出。每个点对大文件 range、小文件合批和 mixed 目录分别测试，至少 5 次重复并改变中断位置；使用显式 failpoint/可审计进程终止，不断电、不重启主机。

**验收：** 恢复后逐文件 SHA-256 和目录清单与源相等；不能把未验证成员发布为已完成；已确认可恢复范围不丢失且不会错误跳过；重传字节和恢复到 `T_ready` 的时间可计算。记录每种语义的支持边界。若当前协议无法满足逐成员身份/独立恢复，E3/E4 不开始。

### E6：真实目录和外部工具上能否复现？

**真实负载：** 先取得可授权、成功结束的科学工作流输出目录；冻结生成器/版本、输入、MPI ranks、输出设置、目标目录内容、文件数/大小分布和 SHA 清单。WRF 输出是优先候选，但必须实际测量其日志/结果比例。若暂时没有 WRF 可运行环境，可使用已有被授权真实输出快照，不声称在 R770 上执行了 WRF 计算。

**外部对照：** 至少测一个语义相容的独立方案。优先候选为 Globus Transfer（若两端有可用 collection/endpoint 与授权），其次为可用的 GridFTP 服务；同时可加入本地可部署的 `tar + ssh`/`rsync` 作为工程参考。Globus CLI 支持递归目录传输和传输后 checksum 验证（[Globus Transfer CLI](https://docs.globus.org/cli/reference/transfer/)）；实际配置、传输/验证语义和版本必须在运行记录中冻结。安装、端点部署、认证服务费用不假设已具备。

外部比较只在相同源/目标、文件集合、可用最终目录语义、checksum/加密设置、协议可用性下进行；把提交任务、打包、解包、校验、重试和发布纳入各自 `T_ready`。不能等价的语义要单列，不能只比较稳态吞吐。认证失败/endpoint 不可达记为 infrastructure unavailable，不是性能失败；GridFTP 使用前检查 GSI proxy 有效期且不记录凭据。

**回答：** E1–E4 的因果结论是否能在真实目录重现；外部工具参考下 CPNetFlux 的适用边界是什么。外部工具跑得更快也是有效结果，应如实报告。

## 6. 论文 go/no-go 规则

- **E1 不成立：** 停止“混合粒度调度是主要瓶颈”叙事，不开发复杂 selector。
- **E2 不成立：** 固定粒度已经足够，移除自适应/预算感知核心主张。
- **E3 不成立：** WorkUnit 不优于强分离调度；论文最多剩下系统工程实现/特定工作负载测量，重新评估投稿价值。
- **E4 不成立：** 可保留统一调度主张，但不保留在线 probe、预算感知和相关题目措辞。
- **E5 不成立：** 性能原型不具备论文所需语义，不用速度收益抵消正确性失败。
- **E6 弱或不可得：** 限制适用性结论，不捏造 HPC 部署或外部基准；投稿前判断证据广度是否足够。

推荐暂定英文题目仅在 E2/E3/E4 支持后使用：*Budget-Aware Work-Unit Planning for Mixed-Granularity Scientific Data Transfer*。若 probe 无净收益，移除 `Budget-Aware`；若 unified 机制无收益，重新评估是否仍值得写成系统论文。

## 7. 实验执行顺序与交付物

### 本次授权执行

1. 做 E0 只读准入盘点；核对上一现场进程均已结束，现有目录未被清理或覆盖。
2. 检查 WRF/其他真实数据、GridFTP/Globus 可用性及安全容量，不输出或复制认证材料。
3. 若 E0 全通过，按 E1 pilot 建立本轮唯一新实验目录，使用当前冻结 V3/raw 配置，先做最小一组验证正确性和资源门；pilot 通过后再做文件数矩阵。
4. 将有效/无效运行、失败、阶段原始记录、输入/目标 tree hashes、环境快照、命令、commit/二进制哈希和清理证据写入 `/home/Su/experiments/CPNetFlux/<本轮唯一目录>/`。报告写到对应实验目录，并给出下一步及是否需要用户裁决。
5. **E1 完成后停止并交回总指挥。** E2–E6 是研究方案，不授权本次对话自行实现原型、改变协议、开始广泛参数扫描或继续占用双机。

### 后续阶段每次必须具备

- 负责人批准的单阶段任务合同与资源/时间上限；
- 固定输入 commit、双端 build 与 binary SHA-256；
- 独立 run ID、数据 manifest、配置和预注册条件；
- 机器/文件系统/网络前后观测、完整性结果、失败归因和清理审计；
- 报告中的准确边界以及下一阶段明确进入条件。
