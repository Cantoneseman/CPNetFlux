# CPNetFlux / GridFTP data encryption A/B 01 analysis

The direct bounded answer is: GridFTP without data encryption completed one resource-clean 1 GiB task at 12.553 Gbps; CPNetFlux with verified data TLS completed one at 19.634 Gbps. Their protected/unprotected counterpart observations were GridFTP-private 8.795 Gbps and CP plain 20.695/19.016 Gbps. These are recorded configurations over local 100GbE TCP and tmpfs, not product ceilings or sustained WAN rates. Both security-mode smokes and external integrity passed.

Data encryption materially changes the GridFTP observation here: clear is about 43% faster than private in the first round. Authentication remains enabled and control still GSI; actual steady-state/CPU/cipher attribution needs repeat coverage. CP data TLS observation is in the same range as its plain observations, so this sample set cannot establish a stable percentage penalty. The apparent first-round 5% decrease is smaller than the plain run-to-run variation. The former 32.5 Gbps mmap result used unsupported-for-TLS optimizations and had a failed resource gate; comparing it to 19.6 Gbps would confound frame size, receive buffer and write path with cryptography.

The initial 4 GiB group stopped on R1 global pswpout +1512 pages despite >24 GiB available memory and zero owned task swap. Its 11.850 Gbps complete private transfer is diagnostic only. A separate plan amendment fixed a new 1 GiB group without relaxing guards. This group stopped on second GridFTP-clear sample: R2 missed/OOB +104, while SHA and RETR/STOR final statuses succeeded. Five of six windows met all resource gates; no arm reached n=3. No median/CV or robust speedup estimate is defensible.

Receive-buffer exhaustion/missed counters are no longer confined to the earlier CPNetFlux mmap window: they now appear during GridFTP clear. This is evidence against treating mmap as a necessary condition. It is not proof the two counter events share one root cause; global/delayed driver accounting and queue-specific pressure must still be investigated. Snapshot queue/softirq/IRQ data is preserved. No system tuning was performed and no stop condition was bypassed.

Next evidence to obtain in a new bounded plan: identify affected receive queue and CPU, correlate IRQ/NAPI/softirq/softnet events with packet/driver counter and TCP retransmit windows, identify global swap activity separately from owned processes/tmpfs residency, then rerun the frozen four-arm matrix after interference is understood. Keep identical supported CP parameters within encryption A/B; record actual data cipher and security semantics if claiming cross-application equivalence. Only after repeated clean 4 GiB+ data and realistic storage/WAN tests can these observations inform deployment expectations.
