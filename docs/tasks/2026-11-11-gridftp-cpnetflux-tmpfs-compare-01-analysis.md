# CPNetFlux/GridFTP tmpfs compare 01 analysis

The missing-proxy blocker is resolved by user-authorized, task-scoped GSI issuance, verification and successful 8 MiB private transfers in both directions. The next obstacle is an observed receive-resource stop gate during configuration screening, not authentication.

There are eight 1 GiB R1->R2 exploratory screening attempts and zero formal samples. Seven windows passed resource gates; the four-lane mmap window completed integrity/commit but incremented R2 rx_missed_errors and global rx_out_of_buffer by 375. It is an observation in a bounded time window, not proof that mmap, application speed, IRQ placement or a hardware queue is the root cause. No system tuning or source fix was attempted. The required pause was obeyed and temporary services/payload were removed.

Do not use the apparent 32.518 Gbps mmap observation as a winner: its resource gate failed. Do not promote the clean 27.340 Gbps two-lane pwrite observation or 8.901 Gbps four-stream GridFTP observation either: each is n=1, input size is only 1 GiB, and controller wait polling added up to about 50 ms. The formal repeated/paired protocol matrix is incomplete. No median, CV, statistically defensible speedup or 100 Gbps ceiling follows.

Security and topology are unequal: CPNetFlux used anonymous/plain V3 TCP with CRC32C verified_chunks, commit_sync=none and no post-write reread; GridFTP used task-local GSI authenticated private data channels in third-party mode. Both used the same .1/.2 100 GbE TCP link and tmpfs endpoints, but this is an operational-configuration comparison, not equal security/durability semantics. Linux doubles requested socket buffer values; actual CP four-lane receive buffer reported 2097152 per socket. Requested 1 MiB is not actual 1 MiB. mmap is four-lane-only, and the receive-buffer experiment is <=4-lane-only; connection-count results cannot be called a pure scaling curve.
