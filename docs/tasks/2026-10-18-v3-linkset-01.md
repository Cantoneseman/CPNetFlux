# V3-LINKSET-01：十链路模型和能力协商

状态：in_progress；LinkSet 模型、GlobalScheduler 兼容视图、能力摘要及 XCPNETFLUX V2 可选控制字段已完成；真实多链路数据面仍未接入。

## 要解决的问题

当前 GlobalScheduler 只管理单个 linkId/LinkState，服务端目录通道上限仍是单一的最多 8 条连接，调度器无法表达每条物理链路的端点、容量、RTT/BDP、队列、在途字节、健康状态和 connection epoch。继续在现有 link0 上叠加连接数会把逻辑连接数误当物理链路数，无法为后续 range 分配和安全 drain/cut 提供可靠状态模型。

## 本阶段范围

1. 增加可独立测试的 LinkProfile、LinkRuntimeState、LinkSet 模型。
2. 校验 link_id 唯一、容量和 pending window 非零、端点绑定不冲突、链路数量不超过本地安全上限。
3. 增加对端能力协商模型：本地请求数量与对端最大链路数、最大 pending window、能力位做交集；只输出安全的 negotiated set。
4. 对 1/2/4/8/10 条链路配置进行解析/构造测试；拒绝重复、零容量、端点冲突和超出对端能力。
5. 提供 weighted least-load/weighted deficit round-robin 所需的选择输入与 choose 接口，但本阶段只验证确定性选择和 reserve/release 记账，不接入真实传输默认路径。
6. 记录现有 scheduler 单链路限制、控制面字段和未来协议兼容点，为 V3-MULTILINK-RANGE-01 留出接口。
7. 提供稳定的能力广告编码、严格解析和协商摘要，供后续控制面适配复用，避免各层重复定义字段校验。

## 非目标

- 不接入真实传输调度器或改变默认策略。
- 不扩大 wire/manifest 格式，不做交换机聚合、RDMA、十链路性能实验。
- 不实现 range 多链路切分、故障迁移或 drain/cut；这些属于后续任务。
- 不把逻辑连接数量报告为物理链路数量。

## 验收标准

- 模型单测覆盖 1、2、4、8、10 链路构造及确定性选择。
- 非法重复 link_id、容量为零、端点冲突、超出对端能力均返回明确错误。
- reserve/release 对每链路 inflight bytes 和 lease 记账守恒；重复释放、未知 lease、超容量 reserve 拒绝。
- 协商结果稳定记录 requested/accepted/rejected/reason，不能静默降级。
- 能力广告的 links/pending_window/capabilities 编码顺序稳定；缺字段、重复字段、未知字段和越界值明确拒绝。
- 相关 CMake/CTest 通过；不改变现有传输 smoke 的实际模式和摘要。
- 结果文档记录输入提交、文件白名单、命令、输出证据和下一步。

## 2026-10-18 XCPNETFLUX V2 控制面承载切片（本轮）

- 实际问题：上一切片只有稳定的内部 LinkSet 能力摘要，控制面没有承载 requested/accepted link count 和 capability bits；客户端无法要求多链路能力，服务端也无法明确接受或拒绝，容易把“默认单链路”误认为“已协商多链路”。
- 本轮范围：在现有 XCPNETFLUX V2 persistent-tree 请求中增加可选 LINKS=<N> LINK_CAPS=<bits>；客户端显式请求时校验服务端回执，服务端按自身能力和安全通道上限进行拒绝或接受；默认不带字段的旧行为保持不变。
- 代码：LinkSet 提供控制字段的严格编码/解码；tree client 增加 --link-set-links 1..10 与 --link-set-capabilities <bits>；control server 增加 --link-set-max-links 1..10 与 --link-set-capabilities <bits>。服务端实际协商仍受现有 kPersistentTreeMaxChannels=8 约束，默认服务端能力为 1 条链路、能力位 0。
- 明确语义：显式请求缺字段、越界、能力位不被服务端覆盖或请求链路数超过 8 时返回 504；客户端收到未包含同等 links/link_caps 的成功回执也失败，不做静默降级。该切片只完成控制面协商，不创建物理链路、不切分 range、不改变默认调度。
- 测试：先以新增控制字段测试得到预期 linker red（/tmp/cpnetflux-runs/V3-LINKSET-01-20261018-control-red.log），再完成实现；目标构建成功（...-control-green-build.log），定向测试 12/12、完整单元测试 333/333、CTest 374/374（0 failed）。完整 CTest 证据：/tmp/cpnetflux-runs/V3-LINKSET-01-20261018-control-ctest.log。
- 实际协议验证：深圳本机 loopback 显式接受、默认兼容和显式拒绝均通过。随后在深圳/上海两台阿里云主机间双向传输：深圳→上海上传 2 文件（134,971 bytes），上海→深圳上传 2 文件（102,265 bytes），两方向源/目的文件 SHA-256 均逐文件一致；跨机默认能力服务端也拒绝 LINKS=2/LINK_CAPS=1，且没有写入目标文件。证据目录为两端 /tmp/cpnetflux-runs/V3-LINKSET-01-20261018-cross；首个反向端口 25300 不可达，改用未占用的独立数据端口 24300 后完成，未停止或改配既有 GridFTP 服务。
