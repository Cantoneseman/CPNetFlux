## 实际问题

V3-MULTILINK-RANGE-01 已让 LINKS/LINK_CAPS 建立独立 TCP data session 和 range lane，但 persistent tree 在全局调度模式下仍拒绝多链路请求；DynamicFileQueue 的 drain、disconnect、recover 状态也没有同步到 LinkSet。因此多链路无法受 GlobalScheduler 统一调度，调度器也无法可靠避开断开的 lane。

## 本轮范围与非目标

本轮将 GlobalScheduler 接入 N 条逻辑 lane，保留单链路默认行为；队列按 LinkSet 的健康状态、归一化负载和范围亲和选择 worker；移除 persistent global scheduler 对 LINKS>1 的拒绝；同步 lane 的 draining、healthy 和 connection epoch。

不开发物理网卡、服务器多 endpoint、local bind、交换路径或线路性能配置；不声称物理多路径或吞吐提升；不改 wire 字段；不做十链路矩阵。

## 验收结果

- GlobalScheduler 支持配置 N 条逻辑 LinkSet lane，默认仍为 1；逻辑 lane 建立独立 LinkManager 身份。
- DynamicFileQueue 的 work claim 经 LinkSet 选择健康 lane；负载相同时以范围偏移/长度稳定破平局，保持多 lane 的范围亲和。
- persistent tree 的 global scheduler + LINKS>1 请求不再被本地参数校验拒绝。
- drain、disconnect、recover 状态及恢复后的 connection epoch 发布到对应 lane。

## 事实边界

本轮证明 GlobalScheduler 驱动两条逻辑 lane 的 persistent tree 双向传输、范围分摊和文件完整性；不证明 lane 对应不同物理网卡或物理链路，也不证明多链路的吞吐收益或故障情况下的端到端自动切换。

## 下一步计划：V3-LANE-FAILOVER-01

解决尚未验收的 lane 级故障隔离：某条 lane drain/disconnect 时，仅将其未提交 range 回收到其他健康 lane；旧 connection epoch 的迟到结果必须被拒绝，已经提交的 range 不重复写入；恢复后以递增 epoch 重新加入 LinkSet。先补有行为含义的队列/lease 测试，再用可控 lane 断连在深圳与上海验证双向完成和 SHA-256。物理网卡及不同物理路径的配置验证按用户要求暂缓，等代码侧故障切换完成后再上服务器配置。
