# R770 接收成本诊断与 5 GiB 准入

2026-11-24，第一阶段通过。两台 R770 的 100 GbE 直连保持 RX/TX 1024/1024。R770-2 向 R770-1 用四条 TCP 连接发送 5 GiB 单文件，启用 inline mmap 后，文件完整提交用时 **1.235 秒，任务速率 34.78 Gbps**。源和目标的外部 SHA-256 一致，5,120 个 1 MiB 分块均通过 CRC32C 及提交记录检查。该样本是单次准入。

## 512 MiB 写入方式对照

使用同一份不可压缩数据、普通 tmpfs、四流 V3 明文 TCP、256 KiB DATA 帧、1 MiB 接收缓冲请求、1 MiB 分块、每 16 块 checkpoint，以及每流 1.5 GB/s 的应用限速。Linux 实际报告四流套接字的接收缓冲均为 2 MiB（含内核加倍后的读回值）。双方关闭压缩。接收端均在数据线程内直接处理，只切换存储写入方式。mmap 把目标文件的有界窗口映射到内存，pwrite 按偏移发起写入系统调用。保持 CRC32C、租约、恢复和提交策略。采用下载路径以使用当前版本的 mmap 功能，年度基线使用上传路径。

| 受测写入方式 | 任务用时，秒 | 以中位用时换算的速率 | 接收进程 CPU 中位，CPU 秒 |
| --- | ---: | ---: | ---: |
| pwrite（2 次） | 0.190 / 0.176 | 23.45 Gbps | 0.654 |
| inline mmap（2 次） | 0.136 / 0.170 | 28.08 Gbps | 0.476 |

测试顺序为 pwrite、mmap、mmap、pwrite。两对中 mmap 均更快，中位任务用时减少 16.5%，接收进程 CPU 减少 27.3%。两个候选都通过硬门。进程定时由子进程退出时的资源统计获取，任务计时为接收客户端进程启动至退出，包含建连、传输和协议收尾。数据生成、服务启动和外部 SHA 单独计时。四流使用默认端口分配，连接落入的接收队列随样本而变。两个 mmap 样本分别落到四个和三个队列，当前样本数量只能作为配置选择依据。

## 接收端成本

另做两次 512 MiB 诊断，每种写入方式一次。内部计时含计时器自身开销，下表用于拆分成本。细项为相同范围的统计，表中两条墙钟指标是各范围用时之和，其余指标为线程 CPU 时间。区间存在嵌套，合计数没有独立含义。

| 接收端 512 MiB 成本 | pwrite | inline mmap |
| --- | ---: | ---: |
| 实际写入 CPU | 490.35 ms | 324.88 ms |
| 读取数据帧 CPU | 89.36 ms | 96.90 ms |
| CRC32C CPU | 8.73 ms | 9.80 ms |
| 帧状态更新 CPU | 1.04 ms | 1.09 ms |
| 租约处理 CPU | 2.32 ms | 2.63 ms |
| 分块 checksum 合成墙钟累计 | 0.33 ms | 0.36 ms |
| checkpoint 墙钟累计 | 2.68 ms | 2.77 ms |

两个诊断各处理 2,048 个 DATA 帧并校验 512 MiB。mmap 共映射、解除映射各八次，写入覆盖完整文件，结束时映射占用归零。实测写入少用约 165 ms 接收线程 CPU，读帧、CRC 和 checkpoint 的差距较小。发送端八个 range 的数据线程 CPU 和生产线程 CPU 分别为 pwrite 方案 0.224 / 0.170 秒，mmap 方案 0.174 / 0.182 秒。发送端细分 wrapper 指标未导出，发送成本用进程、线程和已有 range 统计描述。当前代码的 mmap 要求明文 TCP，256 KiB 帧、缓冲及限速的 TLS 约束由代码和本轮相关测试核对，TLS 的实际性能留给后续阶段。

## 5 GiB 准入与现场

- R2 向 R1 明文 TCP，端点为 192.168.100.2 和 192.168.100.1，接口为 eno17095np0。发送端记录四个 V3 数据通道，客户端完成并验证控制终态。接收接口增加 5,615,522,714 字节，包含 TCP 和协议开销。
- 5,368,709,120 逻辑字节在 1.235 秒内完成，外部目标 SHA 检查另外用时 3.62 秒。SHA-256 为 `867c60a763149bef989bd4f23ee180ee83022256ed1518841f6ee2e41b45f8c0`。
- R1 接收进程用 4.334 CPU 秒（用户态 0.404、内核态 3.930），R2 发送进程用 4.093 CPU 秒（用户态 0.443、内核态 3.650）。R1 最忙的四个线程各至少用了 1.00–1.11 CPU 秒，R2 前四个为 0.47–0.68 CPU 秒。这是以约 25 毫秒为目标间隔读取 /proc 得到的线程下界。接收进程与发送进程分别用 0.87 和 0.82 CPU 秒/GiB。
- R1 主机在客户端执行窗口累计忙碌 4.68 CPU 秒。R2 在发送服务观察窗口累计忙碌 4.70 CPU 秒，包含服务等待、观察及背景工作。两个窗口的主机统计约为 1.88 CPU 秒/GiB。此前年度报告的约 4 CPU 秒/GiB 同样是两台主机窗口的忙碌时间总和，包含背景活动。两台进程的 CPU 秒可分别用来读发送成本和接收成本。
- R1/R2 最低 MemAvailable 为 22.67/23.74 GiB，进程采样 RSS 峰值约 193.1/15.2 MiB。两端无新增 swap 换出、受测进程 swap、全局 full memory PSI、网卡漏包、缓冲不足、CRC 及所采 HCA 错误。R2 系统 TCP 重传计数 +1，R1 为 0，计数范围覆盖整机。
- 七个测试均通过完整性和资源检查。实验数据和临时服务已清理，双机快照显示网卡、路由、原 2121 监听进程与开测前一致。
