# CPNetFlux 单链路 100G 性能提升路线

> 状态：开发计划，不是性能结果或 readiness 结论。更新：2026-11-04。

## 任务范围

目标是在 R770-1/R770-2 单端口 100GbE/RoCE 直连条件下，提升 CPNetFlux V3 对真实文件传输的稳定端到端吞吐，并改善小文件任务完成时间。按证据推进 RDMA 资源治理、三阶段流水线和小文件自适应微批；每项机制都要有独立对照与完整性证据。

输入基线：分支 `codex/V3-GRIDFTP-OPTIMIZED-RERUN-01`，提交 `a4ae9963db17bc061aadcfa8d95d13de6c86849f`。该提交只在此前代码基线上增加 RDMA E2E 基线任务说明；本计划不改传输源码。运行实验前重新核实两端提交、工作树、构建配置和二进制 SHA-256。

## 非目标

- 只验证单条 100GbE 数据路径，不据此宣称 10 条链路的 1Tbps 聚合已实现。
- 不把 `ib_send_bw`、direct bench 或网卡标称速率当成真实文件性能。
- 不预设三阶段流水线、共享缓冲区、SR-Dispatch 或微批是已证实瓶颈。
- 不把 Marlin 论文作为 300Gbps 软件吞吐证据；只参考其并行读/传输/写入与有界暂存思路。
- 不把 CPSS(DCC) 压缩/恢复工作混入 CPNetFlux 数据面，不在本轮宣称论文创新性或生产 readiness。
- 不改变 V3 帧协议、manifest/checkpoint 和原子提交语义，除非后续单独决策并通过恢复测试。
- 不预先引入 RDMA WRITE、HugePages、O_DIRECT、系统 MTU/NUMA 改动或无上限缓存。

## 当前证据与缺口

| 证据 | 已有结果 | 边界 |
|---|---|---|
| 原生链路 | `ib_send_bw` 单 QP/四 QP 基准约 92.59 Gbps | 不包含 CPNetFlux framing、校验、文件 I/O 或任务启动成本 |
| CPNetFlux direct bench | 64 GiB 单连接 payload 中位约 30.35 Gbps；4×64 GiB 四连接组端到端中位约 82.97 Gbps，四 lane payload 速率之和约 92.43 Gbps | 两种计时口径不能混为一谈；不含真实文件落盘 |
| 真实文件 | 历史结果约 3.29 Gbps | 该结果早于 RNR 修复后的正式复测；当前有效目标是重跑 |
| RDMA 内存 | 历史配置约 2.1 GiB 注册接收池/连接；四连接进程 RSS 约 8.25 GiB，建池分配/清零约 1 秒/连接 | 需要核对当前版本；短于接收池容量的测试不足以验证长传输反压 |
| 拓扑 | 每台 R770 当前一张 100GbE/RoCE 端口 | 单端口实验不验证多端口扩展或 1Tbps |

原生链路和 direct bench 的依据见 [2026-11-02 RDMA 长传输结果](2026-11-02-v3-rdma-steady-01-result.md)；真实文件复测范围见 [R770 RDMA E2E 基线任务](2026-11-04-r770-rdma-e2e-baseline-01.md)。

## 指标口径

- `payload_rate`：成功且校验通过的有效 payload bytes / 数据传输区间墙钟。
- `T_ready`：一次传输从任务启动到目标文件校验成功并原子发布的总墙钟，包含建连、初始化、数据、flush/manifest/final verify 和 close。若脚本字段定义不同，报告中说明转换方法。
- `task_rate`：成功有效字节 / `T_ready`。文件目标以此为核心口径；不得相加各线程累计墙钟。
- 每个样本记录方向、数据集、连接数、实际 file-range 并发、setup/steady/close 分段、源/目标 SHA-256、两端 CPU/RSS、文件系统阶段、网络/HCA 计数差值、失败/恢复次数。
- 短时 burst、每 lane 吞吐和不同配置不能合并成一个结果。

## 串行阶段

| 阶段 | 工作 | 进入下一阶段的门槛 |
|---|---|---|
| 0. 固定基线 | 执行当前 [R770 RDMA E2E 基线任务](2026-11-04-r770-rdma-e2e-baseline-01.md)：同提交/同配置构建，比较原生 `ib_send_bw`、CPNetFlux RDMA socket bench 和 V3 真实文件上传/下载；1/4 连接、4/64 GiB、每格至少 3 次；保留 route、接口/HCA 计数、SHA-256、原始日志；证实四连接单文件实际 range 并发。 | 样本都有完整性证据；失败格有可复现原因；稳态与 `T_ready` 分开；得到 post-RNR-fix 真实文件基线。 |
| 1. 瓶颈归因 | 拆解 QP/控制建连、注册/分配/清零、RQ 补投递、CQ 等待、帧复制、checksum、range 调度、文件写入/writeback、manifest/final verify。收集各阶段墙钟和 CPU；可用时增加 `perf stat/record`、线程 CPU、分配次数和 NUMA 观察。 | 至少三个重复样本把主要时间归到明确阶段；不把等待墙钟当 CPU，也不把关闭期 flush 误算成 payload 错误。未归因时继续测量，不并发改多个参数。 |
| 2. RDMA 队列与建连资源 | 以当前 RQ2048 为对照，按每连接接收资源预算测 64/128/256 MiB 档位及长传输；分别观察注册内存、分配/清零、post/repost、RNR、CQ、RSS 和 setup 时间。SQ 深度、CQ 批量/自旋/事件等待逐项测试；保留槽位所有权和有界反压。 | 找到可重复的最低稳定窗口；相对 RQ2048 长传输吞吐回退不超过 5% 的配置作为资源目标候选；样本超过候选池容量并验证恢复/尾包/异常退出。 |
| 3. 三阶段流水线与有界缓冲 | 按测量结果评估生产端读取/发送前 checksum、网络收发、接收端 checksum/写入/manifest 提交三阶段。先比较每进程总计 64/128/256 MiB 有界暂存预算，不按每 lane 无限叠加；记录队列水位、停顿时间、复制字节和 backpressure。沿用并审计已有 bounded payload pipeline。 | 相对同步基线改善真实文件 `T_ready`，并通过 checksum、SIGKILL/resume、原子提交和队列满/空测试；峰值 RSS 在预算内；无明显非目标负载回退。缓冲仅吸收阶段速率短时差，不把容量本身当吞吐收益因果。 |
| 4. 小文件自适应微批 | 先 profile 4/16/64/256 KiB 文件，文件数 1K/10K/100K；对照 tuned native per-file、固定微批、自适应微批。候选输入为文件数、字节量、每文件固定开销、队列/worker 服务率和失败恢复成本。成员保留路径、长度、checksum、原子发布和成员级恢复语义；第一轮不叠加压缩。 | 若 open/manifest/commit 等固定开销占 `T_ready` 主要部分，微批对 native 和 fixed 分别报告收益。研究目标：密集小文件中位 `T_ready` 至少下降 20%，p95 与恢复成本不恶化，大文件吞吐回退不超过 5%。若 adaptive 不优于 fixed，研究贡献降级为工程优化。 |
| 5. 服务率感知调度 | 仅在测到持续 worker 服务率差异、队列偏斜或慢对象拖尾后，引入 SR-Dispatch/lease 对比静态分配、固定并发和无 scheduler。BAP 作为阶段 3/5 候选，不叠加多个自适应环。 | 同一异构负载至少 5 次重复显示完成时间/尾延迟稳定改善，且无公平性、饥饿、恢复或内存回归。同质 worker 或队列未失衡则暂缓。 |
| 6. 单链路稳定验收 | 冻结配置、代码、数据与构建；双向上传/下载及 representative large/dense/mixed 负载各至少 5 次；长传输超过接收池容量。记录 route、bind、计数差值、二进制哈希和完整性。 | 零内容错误/静默降级，SHA-256 全通过，CV ≤5%，没有未解释 HCA/网卡错误；raw evidence 可重算。完成此门后再评估部署 readiness。 |

## 性能目标

以下是阶段工程目标，不是当前成绩、工期承诺或保证值。目标指真实文件，必须同时报告 `payload_rate` 与 `task_rate`。

| 目标级别 | 目标 | 说明 |
|---|---:|---|
| 第一工程里程碑 | 10–20 Gbps `task_rate`，且达到 post-RNR-fix 同负载基线至少 2 倍 | 若基线变化，按新基线解释倍数和绝对值 |
| 中期目标 | 单个大文件经验证的 4-lane range 并发达到 30–50 Gbps `task_rate` | 必须证明同一文件实际并行切 range |
| 单端口冲刺目标 | 70–85 Gbps 稳定 `task_rate` | 需逐阶段成本、存储能力和多次长样本支持 |
| 极限探索 | 85–90 Gbps | 仅在瓶颈证据和稳定性允许时尝试 |
| 当前不承诺 | 100 Gbps 应用有效吞吐或 1 Tbps 聚合 | 92.59 Gbps 是硬件 benchmark 参考，100G 是端口标称线速；十端口需另建路线 |

## 设计约束与研究定位

- 三阶段拆分采用生产者/网络/消费者的有界队列和显式所有权；注册 RDMA buffer、网络在途窗口、应用暂存 buffer 分开记账。总 RSS 按连接数核算。
- 每次只改变一个主要因素；先有对照，再写实现；先本机回归，再双机固定提交验收。
- 微批保留逻辑成员 manifest、成员校验、失败隔离、重试和原子发布，不能只拼成不可恢复的大归档。
- 开题材料中的 SR-Dispatch、BAP、adaptive microbundle 都是研究候选。批处理、文件聚合和流水线已有相关工作；完成相关工作对照前不声称新颖性。BAP 与微批是不同规模问题，不直接包装为多个独立创新点。
- CPSS(DCC) 是独立项目；压缩不进入首轮热路径对照。
- 单链路达到门槛后，10-port/1Tbps 仍需单独定义 NUMA/PCIe/交换网络、聚合策略、故障域和验收拓扑。
