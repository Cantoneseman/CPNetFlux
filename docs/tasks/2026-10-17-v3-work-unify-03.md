## 要解决的实际问题

02 已接通 persistent + global scheduler 与共享 queue，但 sender/receiver 各自推进 lease 状态；恢复仍需调用方手动串联 disconnect/requeue/reopen。新路径容易错用其他 worker 的有效 lease、不完整对账导致工作丢失，或反复增加 attempt。

## 本阶段范围与接口

- 新增 WorkExecutor：共同 claim/incoming/begin/IO/awaitResult/commit/reject/finalize 入口；绑定 worker/link/epoch，拒绝跨 owner handle。
- 将 persistent sender 和 receiver 的已有 queue 路径改为使用该入口；单文件及 global scheduler 通过共用的持久传输函数进入。显式无 queue 的兼容入口继续沿用协议内核，本阶段不宣称全部兼容编排已合并。
- WorkRecoveryDecision 携带完整 lease 与 Missing/Committed 明确结论。disconnect 后的 recover 必须得到该 worker 每个 active lease 的权威对账结论，先验证整个 ledger，再只重派 Missing、释放 Committed、推进 epoch。
- 不把“缺失清单没有列出”当成提交证据。Committed 由调用方核验接收端 manifest/提交状态后提供；recover 不自行访问远端。
- maxRetries 不含初始 attempt（attempt=0）；0 禁止补传，默认 3 只作用于本恢复 API。超过上限、epoch 耗尽、伪造/重复/遗漏/外来 lease 均拒绝且不改变 queue。
- metadata/scheduler IO 失败与既有 claim/commit 一致：queue 进入终止错误，不能继续 reopen；不承诺跨磁盘日志的事务回滚。
- WorkExecutor 的生命周期状态成功不代表传输成功：finalize(失败) 转入 Reclaimable 并保留 credit，须停止/join 旧 transport 后恢复。
- 修复多 range 恢复发布：checkpoint 已验证的 range 不必重派，完整 verified coverage 且无活动 writer 即可提交；同一会话后续未见过的已验证 range 仅允许 skipped 完成，发布后 DATA 仍拒绝。
- queue 是唯一活动 lease owner；executor 不复制另一套 lease 状态。recover 成功刷新 executor owner，恢复前所有使用该对象的 IO/reader 必须退出。

## 非目标及范围细化原因

本轮最初检查自动 transport reconnect；代码显示 sender requestAbort 和目录 cancelAll 会永久 cancel queue，而控制 batch、远端事务和 manifest 对账必须联合重建。单改 requeue 不足以安全实现自动恢复。因此本阶段先交付可验收的共同入口和恢复原语，自动控制面接线独立留给 04；02 的整体有界自动恢复目标继续未完成。

不新增自动 TCP 建连、控制面重新协商或远端 manifest 查询协议；不合并所有兼容 worker loop，不提升默认策略，不做跨机/十链路/RDMA/生产 readiness，不刷新未使用的 GridFTP proxy。
